## 1. 개요

KBO 현역 선수 이름을 하루 한 명 맞히는 데일리 퍼즐입니다. 워들(Wordle)의 격자·색 피드백 구조를 한글 3음절 선수명에 맞게 옮기고, 야구 도메인 힌트(팀·포지션)를 보조 축으로 얹습니다.

**핵심 가치**

- 하루 1회, 2분 안에 끝나는 재방문 루프(퀴즈와 성격이 다름: 퀴즈는 지식, 워들은 추리)
- 정답이 매일 전 유저 공통 → 결과 공유가 자연스럽게 발생(카톡 확산)
- 서버 연산 없음(정적 페이지 + 클라이언트 계산) → Vercel Hobby CPU 제약과 충돌하지 않음

**게임명 — 확정: `오늘 선수는 누구?`**

| 후보 | 평가 |
| --- | --- |
| **오늘 선수는 누구?** (확정) | 질문형이라 게임임이 즉시 전달되고, `맞히다`/`맞추다` 표기 문제를 피한다. 데일리 성격(`오늘`)이 이름에 담기고, 물음표가 공유 시 훅으로 작동한다 |
| 선수 맞히기 | 설명형으로 앱 관례와 맞지만 `맞히다`의 어감이 딱딱하다. `맞추기`는 표기가 틀림(정답은 "맞히다") |
| 야구워들 | 워들을 아는 사람에겐 바로 전달되지만 4글자로 길고, 모르는 사람에겐 의미 불명 |
| 오늘의 선수 | 야구에서 MVP·수훈선수로 읽힘. 질문형으로 바꾸면 이 오해가 사라진다 |
| 야들 | `야들야들`과 충돌해 식감이 먼저 연상됨. `구들`도 온돌 구들장과 충돌 |
| 선수들 | "선수"+"워들" 합성이지만 **펀이 보이지 않는다.** 대부분 "선수 여러 명"으로 읽어 설명도 브랜딩도 실패 |

이름이 길어도 홈 카드는 안전하다 — `play-hub-grid-2`의 제목 스타일이 `word-break: keep-all` + 줄바꿈 허용이고 ellipsis가 없어 잘리지 않는다(`styles/dark-lineup.css`).

물음표로 끝나므로 **공유 텍스트는 제목을 독립 줄로** 둔다. 날짜·점수를 같은 줄에 붙이면 어색하고, 줄을 나누면 물음표가 "너도 해볼래?" 훅으로 읽힌다.

**표시명과 검색어를 분리한다.** 화면에는 질문형 `오늘 선수는 누구?`를 쓰고, "워들"은 페이지 메타데이터에만 넣어 `야구 워들` 검색 유입을 노린다. 둘 중 하나를 포기할 필요가 없다.

경로는 영문 `/play/wordle` 유지 — 개발자에게 명확하고 사이트맵·공유 텍스트에 이미 반영돼 있다.

## 4. 글자 피드백 판정 스펙

### 4.1 분해 단위

각 음절을 (초성, 중성, 종성) 3개 자모로 분해합니다. 종성이 없으면 해당 슬롯은 `null`입니다.

- 겹받침(ㄳ, ㄻ 등)과 복합 중성(ㅘ, ㅙ, ㅚ 등)은 **분해하지 않고 단일 자모로 취급**합니다. 판정 규칙을 단순하게 유지하고, 선수 이름에서 등장 빈도가 낮습니다.
- 슬롯 식별자는 `(음절 인덱스 0에서 2, 자모 종류 초/중/종)`으로 총 최대 9개입니다.

### 4.2 색상 3단계

| 색 | 의미 |
| --- | --- |
| 초록 | 같은 슬롯에 같은 자모 |
| 노랑 | 정답에 있지만 다른 음절 위치 |
| 회색 | 정답에 없음 |

### 4.3 판정 알고리즘 (2패스, 워들 표준 방식)

```
1패스 — 초록 확정
  for i in 0..2, for kind in [초, 중, 종]:
    if guess[i][kind] != null && guess[i][kind] == answer[i][kind]:
      결과[i][kind] = 초록
      answer[i][kind] 를 소진 처리

2패스 — 노랑/회색
  for i in 0..2, for kind in [초, 중, 종]:
    if 결과[i][kind] 이미 확정: continue
    if guess[i][kind] == null: 결과[i][kind] = 빈칸(회색)
    else if 정답의 미소진 자모 중 (같은 kind) 에 동일 자모가 존재:
      결과[i][kind] = 노랑; 해당 자모 1개 소진 처리
    else:
      결과[i][kind] = 회색
```

**중요 결정 — 노랑 판정은 같은 종류(초/중/종) 안에서만 성립합니다.**

예: 추측의 0번 음절 초성 `ㄴ`과 정답의 2번 음절 종성 `ㄴ`은 노랑이 아닙니다. 초성 `ㄴ`과 종성 `ㄴ`은 한글에서 역할이 다르고, 이를 교차 허용하면 노랑이 남발되어 정보량이 오히려 떨어집니다. (중성은 자모 집합 자체가 달라 애초에 교차하지 않습니다.)

**종성 없음 처리**

- 정답에 종성이 있고 추측에 없으면: 해당 슬롯 회색(빈 칸으로 렌더)
- 추측에 종성이 있고 정답에 없으면: 회색. 단 정답의 다른 음절에 미소진 종성으로 같은 자모가 있으면 노랑

### 4.4 판정 예시

정답 `김도영` = [(ㄱ, ㅣ, ㅁ), (ㄷ, ㅗ, null), (ㅇ, ㅕ, ㅇ)]
추측 `김하성` = [(ㄱ, ㅣ, ㅁ), (ㅎ, ㅏ, null), (ㅅ, ㅓ, ㅇ)]

| 음절 | 초성 | 중성 | 종성 |
| --- | --- | --- | --- |
| 김 | 초록 | 초록 | 초록 |
| 하 | 회색 | 회색 | (빈칸) |
| 성 | 회색 | 회색 | 초록 |

성이 맞았고 3번째 음절이 `ㅇ`으로 끝난다는 것까지 확정됩니다.

## 5. 속성 피드백 스펙

추측한 선수의 실제 속성을 정답과 비교해 표시합니다. 정답 선수의 속성을 직접 노출하는 것이 아니라 **일치/불일치만** 보여줍니다.

| 항목 | 표시 | 공개 시점 |
| --- | --- | --- |
| 팀 | 팀 로고(작게). 정답과 같으면 초록 테두리, 다르면 무채색 | 1번째 시도부터 |
| 포지션 그룹 | 투수 / 포수 / 내야수 / 외야수 칩. 일치 시 초록 | 1번째 시도부터 |
| 등번호 | 정답보다 크면 ↓, 작으면 ↑, 같으면 = | **4번째 시도부터** |
| 투타 | 좌/우 일치 여부 | v2 백로그 |

**포지션은 4개 그룹까지만 사용합니다.** 로스터 JSON의 `primaryPosition`은 KBO 원본이 투수/포수/내야수/외야수 4분류만 제공하기 때문에 스크래퍼가 내야수를 `3B`, 외야수를 `CF`로 기본 매핑한 값입니다(`data/rosters/*.json`의 `_note` 참조). 따라서 `3B`, `SS` 같은 세부 포지션은 신뢰할 수 없고, 4개 그룹 수준에서만 정확합니다.

등번호를 4번째 시도부터 여는 이유는 난이도 조절입니다. 팀(10분의 1)과 포지션(4분의 1)만으로도 초반 정보량이 충분하고, 등번호 방향 탐색까지 1번째 시도부터 열면 글자 추리 없이 속성만으로 좁혀지는 게임이 됩니다.

UI 밀도 원칙에 따라 격자 본체에는 팀 로고와 포지션 칩만 붙이고, 상세 설명은 헤더의 `!` 도움말 버튼으로 뺍니다.

## 6. 일일 정답 선정

### 6.1 결정론적 산출 (서버 호출 없음)

```
DAY0 = "2026-07-29"  // KST 기준 0일차 = 배포일
dayIndex = KST 날짜 기준 DAY0 로부터 경과 일수
answer = ANSWERS[dayIndex % ANSWERS.length]
```

`ANSWERS`는 **미리 셔플해 파일에 고정 저장한 배열**입니다. 런타임 셔플이 아니므로 모든 유저·모든 기기에서 같은 정답이 나오고, 서버 API도 DB도 필요하지 않습니다.

### 6.2 정답 풀 스냅샷 고정

로스터 파일은 스크래퍼로 갱신되므로(현재 자동 스케줄은 비활성), 정답 풀을 로스터에서 매번 실시간 계산하면 로스터 갱신 시 배열 순서가 바뀌어 **진행 중인 그날의 정답이 바뀌는 사고**가 발생합니다.

대응: 정답 풀을 별도 스냅샷 파일 `data/wordle/answers.json`으로 커밋하고, 갱신은 수동 스크립트로만 수행합니다.

```
scripts/build-wordle-answers.mjs
  → 로스터 10팀 로드
  → 3음절 && seasonGames >= 30 필터
  → 고정 시드 셔플(날짜 무관, 재실행해도 동일 결과)
  → data/wordle/answers.json 저장
```

배열에 항목을 **추가할 때는 뒤에 append만** 하고 기존 순서는 유지합니다. 그러면 과거 정답 이력이 보존되고, 201일치 소진 이전에 신규 선수를 이어붙일 수 있습니다.

### 6.3 정답 노출 리스크

정답 배열이 JS 번들에 포함되므로 개발자 도구로 미리 볼 수 있습니다. 캐주얼 데일리 퍼즐에서는 일반적으로 허용되는 트레이드오프입니다(꼬들 등 동일). 정답만 서버에서 받아오는 방식은 페이지를 동적으로 만들어 Vercel Hobby CPU 비용을 늘리므로 v1에서는 채택하지 않습니다. 다만 **간단한 난독화(정답 문자열 base64 또는 문자 코드 오프셋)** 는 적용합니다. 우연한 노출을 막는 정도로 충분합니다.

## 7. 입력 방식

### 7.1 v1 — 선수 검색 자동완성 (권장)

- 입력창에 한글 일부를 타이핑 → 3음절 선수 898명 중 필터링된 목록 표시 → 탭해서 선택 → 제출
- 초성 검색 지원(`ㄱㄷㅇ` → 김도영). 자모 분해 유틸을 이미 만들므로 추가 비용이 거의 없습니다.
- 이미 사용한 추측은 목록에서 흐리게 처리
- 장점: 모바일 한글 IME 조합 이슈를 완전히 우회하고, "실제 선수만 추측 가능" 규칙이 입력 단계에서 자동으로 강제됩니다. 구현 범위가 크게 줄어듭니다.

### 7.2 보조 — 자모 현황 패널 (읽기 전용)

커스텀 키보드를 입력 수단으로 쓰지 않으므로, 소진된 자모를 추적하는 정보는 별도 패널로 제공합니다.

- 초성 19자 / 중성 21자 / 종성 27자를 3줄로 나열하고 회색·노랑·초록 상태를 칠합니다.
- 접기/펼치기 가능. 기본은 접힌 상태(정보 밀도 원칙).

### 7.3 v2 대안 — 자유 입력 모드

커스텀 2벌식 자모 키보드로 직접 타이핑하는 하드 모드입니다. 실제 선수가 아닌 조합도 프로브로 쓸 수 있어 전략 폭이 넓어지지만, 키보드 컴포넌트와 조합 상태 관리가 큰 작업이라 v1에서 제외합니다.

## 9. 저장 구조 (localStorage)

미니게임은 localStorage 우선 원칙에 따라 DB를 쓰지 않습니다. 키 접두사는 기존 관례인 `ballplay:` 를 따릅니다.

**진행 상태** — `ballplay:wordle:progress`

```jsonc
{
  "date": "2026-07-28",          // KST 날짜. 다르면 폐기하고 새 판 시작
  "dayIndex": 27,
  "guesses": ["김하성", "김도영"], // 추측한 선수 이름 순서대로
  "status": "won"                 // playing | won | lost
}
```

**누적 통계** — `ballplay:wordle:stats`

```jsonc
{
  "played": 12,
  "won": 10,
  "streak": 4,
  "maxStreak": 7,
  "lastPlayedDate": "2026-07-28",
  "distribution": [0, 1, 3, 4, 2, 0]  // 1에서 6시도 성공 횟수
}
```

- 진행 상태는 `date` 불일치 시 즉시 폐기합니다. 새로고침·앱 재진입에도 같은 판이 이어집니다.
- streak은 `lastPlayedDate`가 어제면 +1, 이틀 이상 전이면 1로 리셋합니다.
- 쓰기 직후 같은 핸들러에서 다시 읽어야 하는 경우 React state가 아니라 localStorage를 우선 읽습니다(기존 라인업 코드와 동일한 이유).

## 14. 성능·제약 고려

- 페이지는 정적으로 유지합니다. 서버에서 `headers()` / `cookies()`를 호출하지 않고 정답 계산도 클라이언트에서 수행하므로 동적 렌더링이 강제되지 않습니다.
- 로스터 JSON 10개 파일을 클라이언트 번들에 전부 넣으면 용량이 커집니다. 워들에는 이름·팀·포지션 그룹·등번호만 필요하므로, `build-wordle-answers.mjs`에서 **추측 풀도 경량 파일로 함께 생성**합니다(`data/wordle/guessable.json`, 필드 4개 x 898명). `lib/rosters/index.ts`를 직접 import하지 않습니다.
- API·DB 호출 0건이므로 Fluid Active CPU 사용량 증가가 없습니다.
