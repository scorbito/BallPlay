# 나만의 커스텀 팀 기획문서

> 작성일: 2026-06-09  
> 상태: 초기 기획안  
> 목적: `나만의 팀` 모드를 기존 BallPlay 기능과 분리된 실험 영역으로 만들고, 이후 안정화되면 기존 경기/시뮬레이션 시스템과 연결한다.

---

## 1. 핵심 컨셉

`나만의 팀`은 사용자가 직접 구단을 창단하고, 실제 KBO 선수 데이터를 기반으로 선수를 모아 자신만의 팀을 만들어가는 수집형 팀 운영 모드다.

선수 개인 성장 시스템은 넣지 않는다. 선수 능력치는 실제 선수 데이터와 시뮬레이션용 스탯을 사용한다. 사용자의 성장은 선수 자체를 강화하는 방식이 아니라, 더 좋은 선수를 영입하고 포지션을 보강하고 라인업을 최적화하는 방식으로 발생한다.

핵심 재미는 다음 루프다.

```text
구단 창단
→ 창단 드래프트
→ 보유 선수로 라인업 구성
→ 경기 또는 다른 콘텐츠 플레이
→ 포인트 획득
→ 선수 뽑기
→ 전력 보강
→ 더 강한 팀 구성
```

---

## 2. 작업 방식

초기 개발은 기존 라인업/경기장/공개 라인업 기능과 최대한 분리해서 진행한다.

### 권장 브랜치

```text
codex/custom-team-mode
```

### 권장 경로

```text
/my-team
```

또는 라우팅/메뉴 네이밍에 따라 다음도 가능하다.

```text
/custom-team
```

### 분리 원칙

- 기존 `bp_lineups` 테이블은 초기 단계에서 건드리지 않는다.
- 기존 라인업 빌더 구조에 바로 섞지 않는다.
- 전용 페이지, 전용 상태, 전용 DB 테이블로 먼저 실험한다.
- 시뮬레이션 엔진 연결은 선수단/라인업/보상 루프가 정리된 뒤 진행한다.
- 기획 변경 가능성이 높으므로 초기 테이블은 단순하게 시작한다.

## 4. 주요 기능

## 4.1 구단 창단

사용자가 처음 `나만의 팀`에 들어오면 구단이 없는 상태로 시작한다.

### 입력 항목

- 구단 이름
- 대표 이니셜
- 팀 뱃지
- 팀 컬러

### 구단 이름

- 예: `단우 베어스`, `서울 파이어볼`, `한강 드래곤즈`
- 글자 수 제한 필요
- 중복 허용 여부는 추후 결정
- MVP에서는 사용자 본인 내 중복만 막아도 충분하다.

### 대표 이니셜

- 1~3글자 권장
- 팀 뱃지에 표시
- 예: `DW`, `BP`, `SB`

### 팀 뱃지

초기 MVP에서는 이미지 업로드 없이 자동 생성한다.

- 이니셜 기반 원형 또는 방패형 뱃지
- 팀 컬러 반영
- 추후 커스텀 로고 업로드 가능

### 팀 컬러

초기에는 선택형으로 충분하다.

- 빨강
- 파랑
- 검정
- 초록
- 보라
- 주황
- 랜덤

## 4.2 창단 드래프트

구단 창단 직후 첫 선수단을 지급하는 단계다.

처음에는 선수가 아무도 없다. 창단 드래프트를 통해 기본 선수단을 만든다.

### 기본 지급 방식

- 타자 드래프트: 3명씩 5번 선택
- 타자 총 15명 획득
- 투수 드래프트: 3명 선택
- 투수 총 3명 획득

### 선수 후보

- 전 구단 실제 선수 풀에서 랜덤 등장
- 기존 KBO 선수 데이터 사용
- 선수 성장은 없음
- 실제 기록 기반 시뮬레이션 스탯 사용

### 드래프트 UX

타자 드래프트 예시:

```text
1라운드: 선수 3명 제시 → 1명 선택
2라운드: 선수 3명 제시 → 1명 선택
...
15라운드까지 반복
```

다만 사용자가 말한 “타자 3명씩 총 5번을 뽑아서 선수 15명”을 그대로 적용하면 아래 방식이 더 자연스럽다.

```text
1회차: 타자 3명 획득
2회차: 타자 3명 획득
3회차: 타자 3명 획득
4회차: 타자 3명 획득
5회차: 타자 3명 획득
총 15명 자동 획득
```

두 방식 중 MVP에서는 구현이 쉬운 `3명씩 자동 획득` 방식이 적합하다. 선택형 드래프트는 이후 재미 요소로 확장 가능하다.

### 초기 선수단 기준

- 타자 15명
- 투수 3명
- 총 18명

이 선수단으로 초반 경기를 시작할 수 있게 한다.

## 4.3 선수단 관리

사용자가 보유한 선수를 확인하고 팀 구성을 관리하는 화면이다.

### 표시 정보

- 선수 이름
- 원소속팀
- 포지션
- 타격/투구 손
- 주요 기록
- 타자/투수 구분

### 필터

- 전체
- 타자
- 투수
- 포지션별
- 원소속팀별

### 포지션 부족 안내

라인업 구성을 위해 부족한 포지션을 보여준다.

예:

```text
포수 부족
유격수 부족
선발 투수 부족
불펜 부족
```

## 4.4 라인업 구성

보유 선수 안에서만 라인업을 구성한다.

기존 라인업 빌더는 특정 KBO 팀 로스터 기반이다. 나만의 팀은 전 구단 선수가 섞일 수 있으므로 별도 라인업 구성 화면을 우선 만든다.

### 타자 라인업

- 1~9번 타순
- 수비 포지션 지정
- DH 사용 여부는 기존 앱 정책과 맞춘다.

### 투수 라인업

- 선발
- 마무리
- 불펜

MVP에서는 투수 3명만으로 시작하므로 최소 구조는 다음과 같다.

- 선발 1명
- 불펜 1명
- 마무리 1명

추후 투수 보유 수가 늘어나면 기존 투수 슬롯 구조처럼 확장한다.

## 4.5 포인트 시스템

포인트는 앱 전체 콘텐츠와 `나만의 팀`을 연결하는 공통 재화로 설계한다.

### 추천 재화명

```text
BP 포인트
```

### 획득처

- 퀴즈 참여
- 승리팀 예측
- 경기장 플레이
- 나만의 팀 경기
- 출석
- 일일 미션
- 이벤트

### 사용처

- 나만의 팀 선수 뽑기
- 추후 팀 꾸미기
- 추후 특별 스카우트
- 추후 이벤트 뽑기

### 설계 방향

전역 포인트를 사용하면 기존 콘텐츠 활성화에 도움이 된다.

예:

```text
퀴즈 풀기
→ BP 포인트 획득
→ 나만의 팀 선수 뽑기
→ 새 선수 영입
→ 라인업 강화
```

### 주의점

- 특정 콘텐츠에서 포인트를 과도하게 얻지 못하게 해야 한다.
- 하루 획득량 제한 또는 콘텐츠별 보상 제한이 필요할 수 있다.
- 나만의 팀을 시작하기 전에 포인트를 너무 많이 쌓아두는 문제도 고려해야 한다.

### MVP 권장

- `BP 포인트` 단일 재화만 사용
- 포인트 로그 테이블을 둔다.
- 잔액은 로그 합산 또는 별도 잔액 컬럼으로 관리한다.
- 초기에는 단순하게 구현하고, 악용 방지는 추후 보강한다.

## 4.6 선수 뽑기

포인트를 사용해서 선수를 획득하는 기능이다.

### 기본 뽑기

- 전 구단 선수 랜덤
- 실제 선수 데이터 사용
- 선수 성장 없음
- 획득한 선수는 내 선수단에 추가

### 뽑기 종류 후보

MVP:

- 전체 선수 뽑기

추후 확장:

- 타자 뽑기
- 투수 뽑기
- 포지션별 뽑기
- 원소속팀별 뽑기
- 고급 스카우트
- 이벤트 스카우트

### 중복 선수 처리

중복 정책은 반드시 정해야 한다.

#### 후보 1: 중복 불가

이미 보유한 선수는 다시 나오지 않는다.

장점:

- 유저 불만이 적다.
- MVP 구현이 단순하다.

단점:

- 장기적으로 선수 풀이 줄어든다.
- 뽑기 긴장감이 줄어들 수 있다.

#### 후보 2: 중복 시 포인트 환급

이미 보유한 선수가 나오면 일부 포인트를 돌려준다.

장점:

- 구현이 쉽다.
- 뽑기 랜덤성을 유지할 수 있다.

단점:

- 사용자는 실패로 느낄 수 있다.

#### 후보 3: 중복 시 스카우트 조각 지급

중복 선수가 나오면 조각을 지급하고, 조각으로 원하는 선수를 교환한다.

장점:

- 장기 플레이에 좋다.

단점:

- MVP에는 무겁다.

### MVP 추천

초기에는 `중복 불가`가 가장 안정적이다.

## 4.7 경기

나만의 팀으로 경기를 플레이하고 포인트를 얻는다.

### 경기 유형 후보

MVP:

- 내 팀 vs AI 팀

추후:

- 내 팀 vs 다른 유저의 커스텀 팀
- 내 팀 리그전
- 시즌 모드
- 랭킹전

### 시뮬레이션

기존 시뮬레이션 엔진을 활용할 수 있다.

다만 기존 엔진은 `teamId`와 `SavedLineup` 구조를 전제로 하므로, 나만의 팀 선수단을 `SimTeamInput`으로 변환하는 별도 어댑터가 필요하다.

### 경기 보상

- 기본 참여 보상
- 승리 보너스
- 연승 보너스
- 일일 첫 승 보상

MVP에서는 단순하게 시작한다.

```text
패배: 소량 포인트
승리: 기본 포인트 + 승리 보너스
무승부: 중간 보상
```

## 5. 데이터 설계 초안

초기에는 전용 테이블을 사용한다.

테이블 접두어:

```text
bp_custom_*
```

## 5.1 bp_custom_teams

사용자가 창단한 커스텀 팀 정보.

```sql
create table public.bp_custom_teams (
  id uuid primary key default gen_random_uuid(),
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  name text not null,
  initials text not null,
  primary_color text not null,
  secondary_color text,
  badge_style text not null default 'shield',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

### 정책

- 사용자당 MVP에서는 1팀만 허용 권장
- 추후 여러 팀 운영 가능

---

## 5.2 bp_custom_team_players

커스텀 팀이 보유한 선수 목록.

```sql
create table public.bp_custom_team_players (
  id uuid primary key default gen_random_uuid(),
  custom_team_id uuid not null references public.bp_custom_teams(id) on delete cascade,
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  player_id text not null,
  source text not null default 'draft',
  acquired_at timestamptz not null default now(),
  unique (custom_team_id, player_id)
);
```

### source 후보

- `founding_draft`
- `point_draw`
- `event`
- `admin_grant`

## 5.3 bp_custom_team_lineups

나만의 팀 전용 라인업 저장.

MVP에서 라인업을 localStorage로만 실험할 수도 있지만, 전용 DB 테스트를 위해 테이블을 두는 편이 좋다.

```sql
create table public.bp_custom_team_lineups (
  id uuid primary key default gen_random_uuid(),
  custom_team_id uuid not null references public.bp_custom_teams(id) on delete cascade,
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  batting jsonb not null,
  pitching jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (custom_team_id)
);
```

---

## 5.4 bp_point_ledger

앱 전체 공통 포인트 로그.

```sql
create table public.bp_point_ledger (
  id uuid primary key default gen_random_uuid(),
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  amount int not null,
  reason text not null,
  ref_type text,
  ref_id text,
  created_at timestamptz not null default now()
);
```

### amount

- 획득: 양수
- 사용: 음수

### reason 후보

- `quiz_reward`
- `prediction_reward`
- `stadium_reward`
- `custom_team_match_reward`
- `custom_team_draw_spend`
- `admin_adjust`

### 잔액 계산

MVP에서는 로그 합산으로 계산 가능하다.

```sql
select coalesce(sum(amount), 0)
from public.bp_point_ledger
where owner_user_id = auth.uid();
```

트래픽이 늘면 별도 잔액 테이블 또는 RPC로 보강한다.

## 5.5 bp_custom_team_draws

선수 뽑기 기록.

초기에는 필수는 아니지만, 디버깅과 밸런스 조정을 위해 저장하는 것이 좋다.

```sql
create table public.bp_custom_team_draws (
  id uuid primary key default gen_random_uuid(),
  custom_team_id uuid not null references public.bp_custom_teams(id) on delete cascade,
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  draw_type text not null,
  cost int not null,
  player_ids text[] not null,
  created_at timestamptz not null default now()
);
```

## 9. 핵심 의사결정 필요 항목

다음 항목은 구현 전 결정이 필요하다.

1. URL은 `/my-team`으로 할지 `/custom-team`으로 할지
2. 사용자당 커스텀 팀은 1개만 허용할지
3. 창단 드래프트는 자동 지급형인지 선택형인지
4. 중복 선수는 불가 처리할지, 환급 처리할지
5. 포인트는 전역 `BP 포인트`로 확정할지
6. 포인트 획득처별 보상량
7. 선수 뽑기 1회 비용
8. 투수 3명 시작이 경기 진행에 충분한지
9. 나만의 팀 경기 상대를 어떤 방식으로 만들지
10. 기존 경기장 메뉴와 언제 연결할지

## 10. 현재 추천안

현재 단계에서 가장 안전한 추천안은 다음과 같다.

- URL: `/my-team`
- 사용자당 커스텀 팀: 1개
- 창단 드래프트: 자동 지급형
- 초기 지급: 타자 15명, 투수 3명
- 선수 데이터: 실제 KBO 선수 데이터
- 선수 성장: 없음
- 포인트: 전역 `BP 포인트`
- 중복 선수: MVP에서는 중복 불가
- 기존 `bp_lineups`: 초기에는 변경하지 않음
- 전용 테이블: `bp_custom_teams`, `bp_custom_team_players`, `bp_custom_team_lineups`, `bp_point_ledger`
- 기존 시뮬레이션 연결: MVP 후반 또는 2차

## 11. 한 줄 정의

`나만의 팀`은 실제 KBO 선수 데이터를 바탕으로 사용자가 직접 창단한 구단에 선수를 모으고, 포인트를 통해 선수단을 보강하며, 자신만의 라인업을 완성해가는 BallPlay의 장기 성장형 수집 모드다.
